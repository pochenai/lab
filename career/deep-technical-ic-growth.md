# 深度技术型 IC 成长路线：从 Feature Builder 到 System Builder

> 这份文档的目标不是追逐职级，而是建立一种可持续的能力：从真实、反复出现且重要的工程痛点中，提出正确的问题，形成新的抽象，并把它做成其他人能够依赖的系统。

## 1. 北极星：技术抽象与影响半径同时扩大

深度技术型 IC 的成长，不应简单理解为“少写代码、多做协调”。更准确的坐标系是：

```text
Technical Abstraction
▲
│                         Distinguished
│                    ●
│              Principal
│                 ●
│          Staff
│            ●
│     Senior
│       ●
└──────────────────────────────► Impact Radius
```

评价单位会逐步变化：

```text
code → component → system → platform → ecosystem
```

这不是说每个人都必须走到最右端，也不是说要放弃亲自实现。关键变化在于：你解决的问题是否更基础，解决方案是否更可复用，受益者是否更多，影响是否更持久。

对偏分布式系统、性能优化、存储、执行路径和基础设施的工程师而言，理想成长路径是：

```
20s / early 30s (Feature Builder)
──────────────
成为极强的 engineer
distributed systems
performance
protocol
database
AI infra

        ↓

30s (Abstraction Designer -> System Builder)
──────────────
提出自己的 abstraction
创造自己的 system
做重要 OSS / infrastructure

        ↓

30s–40s (Problem Finder)
──────────────
找到真正重要的问题 
System → Product
可能创业 / CTO / Technical Fellow

        ↓

40s+
──────────────
Platform / Ecosystem
培养其他技术人才
投资新的技术方向
解决更大的问题

        ↓

最终衡量：

不是
“我赚了多少钱？”

也不只是
“我是什么 Level？”

而是

“因为我做过这些事情，
世界上多了什么以前不存在的东西？”
```

Staff、Principal 或 Distinguished 可以是这条路径的组织性结果；它们不应取代路径本身。


## 2. 当前阶段的核心跃迁--抽象设计新系统

已有优势是能够进入复杂的既有系统，理解架构与执行路径，定位性能或语义问题，实现功能、优化并通过 benchmark 验证。这是非常扎实的系统工程基础。

下一阶段的缺口不是再多完成一些 feature，而是练习从重复痛点走向新的系统：

```text
已有框架
  ↓
理解约束与问题
  ↓
实现 Feature / 优化 / Benchmark
  ↓
Production
```

在此前增加一层：

```text
观察大量真实问题
  ↓
识别重复模式
  ↓
重新定义问题
  ↓
提出抽象边界
  ↓
小型原型验证
  ↓
系统设计
  ↓
产品化并让其他人依赖
```

不要把目标误设为“凭空提出一个宏大的新项目”。有价值的系统通常不是从“我要创新”开始，而是从某些限制在不同任务、不同团队、不同时间里不断重现开始。

## 3. 两条值得研究的样本路径

### Jeff Dean：从重复工程痛点到通用计算抽象

MapReduce 的重要性不只在它的实现，而在于它重新识别了问题：许多看似不同的数据处理任务，重复面对分片、调度、容错、数据移动、局部性和负载均衡。

```text
不同业务任务
    ↓
反复处理同一组分布式系统问题
    ↓
抽象出 map / reduce 编程模型
    ↓
由底层系统统一处理复杂性
```

应学习的不是某一个 shuffle 细节，而是这条能力链：

**重复模式识别 → 抽象边界 → 系统化实现 → 大规模复用。**

### Amin Vahdat：当优化不足时，改变架构假设

网络、数据中心与 AI 基础设施的演进体现了另一种关键判断：当规模、流量、硬件或工作负载发生质变时，旧架构的隐含假设可能已经失效。此时继续把原系统优化 10%，未必是正确答案。

需要练习的问题是：

> 当前瓶颈究竟是实现问题，还是架构假设已经不适用于新的规模与 workload？

这条路线特别适合性能和基础设施工程师：让真实的 scale pressure 驱动新架构，而不是为了“造系统”而造系统。

### 10× scale test：把未来规模当作架构检验器

对每一个关键系统，都应明确问一次：

> 如果请求量、数据量、节点数、并发度或团队使用者在两三年内增长到现在的 10 倍，哪一项假设会最先失效？

这不是要求为遥远的 10× 规模预先把所有东西做复杂，更不是把“可能扩展”当作拒绝交付的借口。它是一个帮助识别架构边界的 thought experiment：

```text
当前 workload
  ↓
列出正确性、性能、恢复与运维上的关键假设
  ↓
将一个或多个压力变量提高 10×
  ↓
找出第一个失效点
  ↓
判断：局部优化、容量规划，还是抽象 / 架构调整？
```

需要检查的常见维度包括：

- **数据规模**：索引、数据布局、冷热分层、compaction、recovery 是否仍可接受？
- **请求与并发**：锁竞争、队列、tail latency、背压和隔离是否仍然成立？
- **节点与地域**：协调开销、数据移动、故障域、网络拓扑和一致性协议是否成为主导成本？
- **状态与策略复杂度**：更新、承诺、验证、reorg / rollback 语义是否仍能保持确定性？
- **组织使用规模**：接口、测试、发布、可观测性和 ownership 是否允许多个团队独立、安全地使用？

10× test 的产出应是一份简短而具体的结论：当前设计可以安全扩展到哪里；触发重构的 leading indicators 是什么；以及一旦超过阈值，下一层架构应朝哪个方向演进。这样，架构演进来自可观察的压力，而非抽象的焦虑。

## 4. 从 Feature 到 System Ideas Notebook

每次实现一个feature都要向上追问如下问题，将其沉淀为 System Ideas Notebook。为每个值得记录的真实问题写一页，不要求公开，也不要急于写代码。建议用同一模板：

```markdown
## 问题名称

### 真正的问题
用一句话描述用户、系统或组织真正承担的代价。

### 现有抽象
当前系统为何以这种方式划分边界？它解决了什么？现有架构为什么不能处理feature？

### 隐含假设
它依赖哪些规模、workload、硬件、可靠性或操作假设？

### 已发生的变化
scale / workload / hardware / requirement
哪些条件变了，使这些假设不再可靠？

### 根本瓶颈
真正受限的是 CPU、I/O、数据布局、协调、协议语义、恢复、可观测性，还是组织接口？

### 新抽象
若不受当前实现束缚，职责与数据边界该如何划分？

### 最小系统
为验证该抽象，最少需要哪些组件与不变量？

### 评估方法
哪些 workload、baseline、指标和失败场景能证明它是否更好？

### 下一步
记录、调研、设计文档、原型，或明确放弃的理由。
```

Notebook 的价值不在于每个想法都落地；它让 problem finding 和 abstraction 像实现能力一样，通过重复获得反馈。一个被放弃的想法只要澄清了约束和假设，仍是有价值的产出。

## 5. 用“五问法”阅读系统论文

读系统论文时，不以“如何复现实现细节”为首要目标，而固定回答五个问题：

1. **此前如何解决？** 旧方案、旧接口与旧操作方式是什么？
2. **什么压力改变了局面？** 是规模、延迟、成本、可靠性、硬件还是 workload 发生变化？
3. **真正的新洞见是什么？** 作者重新看见了什么重复模式或关键约束？
4. **引入了什么抽象？** 新接口替调用者隐藏了哪些复杂性，又暴露了哪些选择？
5. **为什么必须是这样的系统架构？** 数据路径、控制路径、故障处理、隔离和评估如何支撑这个抽象？

以 MapReduce 为例：过去每个分布式应用自行处理并行与容错；数据规模带来压力；大量任务可表达为 map + reduce；这个编程模型成为抽象；调度、分区、shuffle、数据局部性和故障恢复因此成为底层系统责任。

每月选择一到两篇与当前领域直接相关的论文或高质量设计文档，完成一页五问笔记。重点是形成自己的判断，而不是积累阅读数量。

## 6. 从想法到系统的工作方式

一个成熟的系统机会通常经过以下阶段：

```text
真实痛点
  ↓
清楚的问题陈述
  ↓
现有方案与约束调查
  ↓
候选抽象与设计取舍
  ↓
最小原型
  ↓
有代表性的 benchmark / failure test
  ↓
设计修正或放弃
  ↓
产品化：接口、迁移、可观测性、文档、运行保障
  ↓
其他人能独立采用与扩展
```

应把“原型结果否定原假设”视为成功的研究结果，而不是失败。越早得到这种结论，越节省投入。

### 写设计文档时的最低标准

- 问题必须可被反驳：说明谁在什么条件下承担了什么代价。
- 明确旧方案的适用范围，而不是把旧方案简单描述为错误。
- 给出至少一个可行替代方案及取舍。
- 写明不可违反的语义、不变量与故障恢复要求。
- 定义成功和失败的 benchmark，包括 tail latency、吞吐、资源成本、恢复、正确性与操作复杂度。
- 说明最小验证范围，以及何时应停止投入。

## 7. 一年、季度与月度的训练节奏

### 年度目标：培养系统肌肉

年度目标不应是 merge 多少 PR 或看完多少课程，而是建立足够多的“问题定义—抽象—验证”循环。可将“一年提出 10 个 System Ideas”作为参考漏斗：

```text
10 个问题陈述
  ↓
5 个深入调研
  ↓
3 份设计文档
  ↓
2 个最小原型
  ↓
1 个被真实采用、或得到明确证伪结论的系统性尝试
```

它衡量的是练习密度，而不是产出数量：10 个想法不意味着要做 10 个项目。大多数候选应在调研、设计或原型阶段被筛掉；这正是以较低成本寻找值得长期投入问题的过程。

这些数值是节奏参考，不是为了填表。最后一项中“被明确证伪”也应视为成果：它说明错误假设被及时识别，避免了在伪问题上继续投入。若某个方向已经产生高质量的真实影响，应优先深入，而不是机械增加想法数量。

### 季度目标：从观察到证据

每季度选择一个与主领域相邻、且正在经历真实压力的问题：

- 记录 2–3 个新的问题陈述；
- 对其中至少 1 个完成现状、假设和 baseline 调研；
- 形成 1 份可讨论的设计文档或调研备忘；
- 为正在推进的项目补齐一个可复用的 benchmark、profiling 工具、测试框架或运行手册；
- 做一次面向同事的技术分享，获取反例和约束，而不是只展示结论。

### 月度目标：保持最小但连续的复利

- 新增至少 1 条 System Ideas Notebook 记录；
- 将一个已完成工程成果写成“问题—根因—取舍—结果—复用方式”的短文；
- 完成 1 篇系统论文或设计文档的五问笔记；
- 更新个人 impact log，记录量化结果、本人角色、跨团队受益者和可复用资产；
- 与 manager 或可信技术同伴校准一次：当前工作是否在靠近目标领域与更大的影响半径。

## 8. KPI：衡量能力，而不是衡量忙碌

KPI 应同时覆盖输入、学习闭环、结果和影响，避免只奖励 ticket 数、提交量或在线时长。

| 维度 | 可观察指标 | 好的信号 |
| --- | --- | --- |
| 问题发现 | 高质量问题陈述、跨项目重复模式记录 | 能说清问题为何重要，而不只会描述需求 |
| 抽象设计 | 设计文档、替代方案、明确不变量 | 能指出旧抽象何时失效，并提出新边界 |
| 证据能力 | benchmark、profiling、故障测试、baseline 对比 | 结论由数据支持，且能被别人复现或挑战 |
| 系统落地 | 原型、接口、迁移、可观测性、运行保障 | 不止 demo，能安全地被他人采用 |
| 可复用杠杆 | 工具、库、流程、文档、平台能力 | 同类问题不再被每个团队重复解决 |
| 影响半径 | 使用者数量、团队数量、外部社区反馈 | 影响从个人与组件扩展到系统和平台 |
| 领域信誉 | 他人主动咨询、技术决策参与、公开输出 | 逐渐形成“这个领域找你”的认知 |

### 对结果做量化，但不迷信单一数字

尽量记录：

- p50 / p99 延迟、吞吐、内存、磁盘、网络和成本变化；
- 故障类别是否被消除，恢复时间是否下降；
- 发布周期、排障时间、人工操作和回归风险是否减少；
- 有多少项目、团队、用户或外部开发者采用；
- 复杂度是否从每个调用方重复承担，转移为统一、可维护的基础能力。

数字需要配合正确性、可靠性和运维复杂度一起解释。一个 TPS 提升如果牺牲了恢复语义或制造了不可运营的系统，并不是高质量系统成果。

## 9. 70 / 20 / 10 的投入分配

为避免学习面过宽、主线不清，可以采用：

```text
70%  主领域：解决组织真正重要的问题，建立“这类问题找你”的认知
20%  邻近扩展：设计、benchmark、跨团队协作、指导与系统接口
10%  未来下注：论文、原型、OSS、新的硬件或技术方向
```

这个模型的价值在于让未来下注不被日常需求完全吞掉；今天的 10%，可能在三年后成为主领域。

## 10. 每半年复盘：是否真的在变成更高杠杆的 IC

| 复盘问题 | 低杠杆状态 | 正在成长的状态 |
| --- | --- | --- |
| 我解决的是什么？ | 被分配的任务 | 自己识别的重要问题 |
| 我的 scope 是什么？ | 单一 feature | 系统或技术领域 |
| 谁在执行？ | 几乎只有自己 | 多人基于我的方向协作 |
| 谁受到影响？ | 自己或单一团队 | 多团队、组织或外部用户 |
| 时间尺度？ | 一个 sprint | 一到三年的演进方向 |
| 别人如何描述我？ | 代码写得强 | 某个关键领域需要找的人 |
| 产出是否可复用？ | 合并一个变更 | 留下一套工具、接口、系统或方法 |

如果右侧比例持续增加，就在从 Senior 的“解决复杂问题”逐步走向 Staff/Principal 型的“让一个技术领域变得更好”。
