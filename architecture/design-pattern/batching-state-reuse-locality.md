# Batching / State Reuse / Locality：性能数据结构的四种复用

> 核心一行：**优化 = 把"重复发生的开销"变成"一次性建立的结构"。**
> 四种技术手段不是四个独立技巧，是同一条规则作用在四种不同的重复开销上。

## 1. 解决什么问题

树/索引类结构的真实性能问题，通常**不是"访问一个节点慢"**，而是同一件事被重复做了很多遍：

```
① 每个操作各自做一遍准备（定位、划分、去重）    → 重复准备
② 同一棵树的同一段路径，被 N 个操作各走一遍    → 重复遍历
③ 每个操作都新建一批临时容器，用完即弃         → 重复分配
④ 逻辑上紧挨着的节点，物理上散在内存各处       → 每次访问都在等 cache
```

**四个问题彼此独立**（少解决一个，另外三个照旧存在），所以必须分别下手；
也正因为独立，它们很容易被当成四个不相干的技巧来记。

但下一节会看到：**问题独立 ≠ 手段独立。解决它们的顺序是强制的。**

### 这套结构由三个部件 + 一个输入约定组成

先看清谁负责哪个问题（**顺序关系留到 §2**，这里只讲组成）：

```
                     SparseTrie
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
    SlotMap           Cursor           Buffer        ← 三个部件
        │                │                │
  访问不 hash        不重走前缀       不重复分配
  布局可重排         可暂停/可搬走    capacity 保留
        │                │                │
        ▼                ▼                ▼
     ④ 等 cache      ② 重复遍历      ③ 重复分配

     ① 重复准备 ── 不由部件解决，靠"批量 + 排序"这个输入约定；
                    而排序同时是 ② 和 ④ 成立的前提。
```

下面统一用 ①②③④ 编号，§2 的四种技术手段与之一一对应。

## 2. 定义

> **把重复发生的开销，变成一次性建立的结构。**

"重复开销"有四种，所以"复用"也有四种——这就是本文件的骨架：

| # | 复用什么 | 技术手段 | 一次性建立的东西 | 效果落在哪一维 |
|---|---|---|---|---|
| ① | 准备工作 | **Batching + 排序** | 一次排序、一次批量路由 | 减少**次数** |
| ② | 遍历状态 | **Stateful cursor(reuse)** | 一个长期存在的游标 | 减少**次数** |
| ③ | 内存分配 | **Scratch buffer(resuse)** | 一块长期存在的 workspace | 减少**单位开销** |
| ④ | cache line | **Compaction / 重排(locality)** | 一次物理布局重排 | 降低**单次成本** |

四者有**严格的依赖顺序**，不是并列清单：

```
⓪ 容器长期存在（arena / scratch）
   │
   ├──► ③ allocation 复用              ← 只依赖 ⓪，与遍历方式无关
   │
   └──► ① 批量 + 排序
              │    相邻 key 才有公共前缀
              ▼
        ② 游标增量遍历
              │    省掉重复下降
              ▼
        ④ 压实 / 重排布局 ──► cache line
              ▲
              └── 对齐目标 = ①② 稳定下来的那个"逻辑访问顺序"
                  （没有它，连该按 BFS 还是 DFS 排都无从判断）
```

**跳过任何一步，后面那步的收益就近乎为零**——这是为什么它们必须被当成一条链来设计。

> **这里的 ④ 就是 [`indirection-generational-handles.md`](./indirection-generational-handles.md) 的 ④——同一个节点，两篇从相反方向走到它。**
> 那篇把它当**动机**（"要能重排物理布局"是引入 handle 层的根源诉求）；
> 这篇把它当**收尾**（前三步稳定了逻辑访问序，重排才有对齐目标）。
> 而它能不能成立，取决于那篇有没有把 handle 层做出来——裸引用结构里没有"改写全部引用"这件事的落脚点。
> **互为前提，但论证起点不同。**

## 3. 四种技术手段

### 3.1 ① Batching + Sorted —— 复用的是"准备"

把 N 个小操作并成一个批量操作，并且**让批内元素有序**。

```rust
nodes.sort_unstable_by_key(|n| n.path);                    // reth reveal_nodes
sorted.sort_unstable_by_key(|entry| entry.1);              // reth update_leaves
```

排序的收益有两层，第二层才是重点：

1. 相邻 key 共享前缀 ⇒ 下面的游标复用才有意义（否则公共前缀 ≈ 0，游标每次都要弹到根，退化成"每次从根重走"）
2. **前缀连续 ⇒ 可以把"整段属于同一子树的元素"一次切走** ⇒ 并行的划分单位免费得到

```
排序后：123456 123789 123abc │ 124xxx 125xxx
        └──── 全在子树 "12" ──┘ └─ 子树 "12"… ─┘     ← 一条 while 扫出边界
```

代价：`O(N log N)`，通常可忽略。**它是后面一切的入场券，不是可选项。**

### 3.2 ② Stateful cursor —— 复用的是"遍历状态"

无状态遍历每次从根重来；有状态游标把"我走到哪了"物化下来，下次从附近继续。

```rust
cursor.reset(arena, root, path);        // 一次
for key in sorted_keys {                // N 次复用同一个游标
    cursor.seek(arena, key);            // 只弹掉分叉的那几层，只下推那几层
}
cursor.drain(arena);
```

关键认知：**一个能支撑"遍历期间还会改结构"的游标，要保存的东西远不止 `current_node`：**

```
游标 ⊇ { 当前节点, 完整祖先链, 当前绝对路径, 深度, 每层续读位置, 脏状态传播通道 }
```

**它保存多少东西，取决于数据结构本身缺多少东西。** 这是判断"该不该写游标"的唯一标准：

| 数据结构给不给 | 游标要不要自带 |
|---|---|
| 父指针（HashMap 靠 key 前缀可算；`Box` 树要显式 parent 字段） | 不给 ⇒ 自带（栈） |
| 节点的绝对位置/路径（HashMap 的 key 就是） | 不给 ⇒ 自带（`entry.path`） |
| 递归栈 | 需要可暂停/可搬走 ⇒ 自带（显式栈） |

> 所以在 arena 表示里，游标**首先是可行性问题，其次才是性能问题**——不补父链和路径，自底向上算 hash、脏冒泡、结构手术根本写不出来（不是慢，是不可能）。
> 前缀复用是真实收益，但它是**第二阶**的。

判据（反证法）：**纯只读的点查不需要游标**。reth 的 `find_leaf_in_arena` 就只用一个 `Index` + 一个偏移计数器，不碰游标。所以游标的定位是"**带可写上下文的遍历**"，不是"遍历"。

### 3.3 ③ Scratch buffer —— 复用的是"内存分配"

一块长期存在的工作区，操作之间只 `clear()` 不释放，capacity 得以保留。

```
✓  op1 → use → clear → op2 → reuse → clear → op3 → reuse …
❌  op1 → allocate → use → free → allocate → use → free …
```

省的是 allocator 往返、页触碰、可能的清零。热路径上每次操作都要填几百字节到 KB 级的编码缓冲，这个差价值得一个 struct。

两个必须避开的坑：

1. **别把"输出累加器"塞进"scratch"**。它生命周期更长（跨多个操作累积、被 `take()` 走），语义也不同。reth 的 `ArenaTrieBuffers` 就把 `updates`（输出）和 `rlp_buf`（scratch）和 `cursor`（遍历位置，且**故意不被 `clear()` 覆盖**）塞进了同一个 struct——名字不准，4 个成员 3 套生命周期。
2. **"复用 capacity"和"减少遍历"是两笔账**，别混着算：capacity 靠的是容器对象长期存在并原地复用（`Vec::clear` 保留 capacity），收益来自减少 tree walking 的是排序 + 增量 seek。

### 3.4 ④ Compaction / 重排 —— 复用的是"cache line"

让**物理顺序 ≈ 逻辑访问顺序**：

```
不压实：Parent@100   ChildA@9000   ChildB@3500      ← 每次批访问都 cache miss
压实后：Parent, ChildA, ChildB, 祖父, 祖母, …        ← 一段连续地址
```

**为什么"不重排就没有"：** 只要容器会回收空位并复用（arena 的 free list），插入顺序就 ≠ 逻辑顺序，局部性必然随时间退化。所以压实是**周期性的必要维护**，不是可选优化。

**要压实哪种顺序，取决于你的热点是哪种批访问：**

| 布局 | 得到的连续性 | 适合 |
|---|---|---|
| BFS 层序 | 同级连续、**兄弟连续** | 热点是"批量读一个父的全部孩子" |
| 前序 DFS | **整棵子树连续** | 热点是"沿一条路径往下走" |

reth 两层用了**相反**的策略：上层 arena（≤273 slot，热点是 root 的 16~256 个孩子 + 全表线性扫）BFS；子树 arena（可达 10⁵ 节点，热点是按 path 往下 seek）前序 DFS。

> 注意"父和它的孩子放在一起"是**误解**。BFS 给出的是兄弟相邻，父在上一层末尾，并不相邻。
